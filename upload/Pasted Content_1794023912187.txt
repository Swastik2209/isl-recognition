# 1. UNDERSTAND THE PROJECT

The project is called **AccessBridge**.

Its purpose is to create a single, accessible, laptop-friendly web application that helps people communicate using different input and output methods.

Instead of forcing users to switch between separate applications, AccessBridge should bring together four core features:

1. Sign to Text — convert supported hand signs into text using a webcam.
2. Morse Decoder — translate Morse code into readable text.
3. Captions — convert speech into live text using the microphone and supported browser speech-recognition technology.
4. Read Aloud — convert written text into speech.

All four features should connect to a shared text workspace, allowing a user to combine, edit, copy, and read aloud the text generated by different modules.

This is primarily a **laptop-based web application**. Do not make Arduino, external sensors, specialist hardware, or a dedicated physical device necessary.

The final product should be usable by someone who has no programming experience.

## Core principle

A person should be able to open AccessBridge, choose a communication method, use it, and transfer the resulting text into a common workspace with minimal confusion.

Build the actual software, not merely a demonstration of what the software might look like.

# 4. PHASE THREE — IMPLEMENT THE FOUR CORE FEATURES

## FEATURE A — SIGN TO TEXT

Build a genuine webcam-based recognition feature.

### Required interface

The user should be able to:

- Open the Sign to Text section.
- See a clear explanation of supported gestures.
- Request camera access when they activate the feature.
- See the webcam feed.
- Start or stop recognition.
- See the recognized text.
- See whether the system is recognizing a gesture, waiting for input, or unable to classify the current input.
- Review the recognition result before adding it to the shared text workspace.
- Retry or clear the current result.
- Continue using the rest of the application if camera access is unavailable.

### Recognition implementation

Inspect suitable existing repositories and available recognition models before selecting an approach.

Prefer a real recognition pipeline using an appropriate existing model, hand-landmark detector, or documented classifier rather than fabricating results.

If a pre-trained model is available and suitable, integrate it properly. Understand its input format, preprocessing, labels, dependencies, model files, and inference requirements.

Make sure the predicted labels match the gestures the model was actually trained to recognize.

If a model is used, provide its source, license, installation requirements, supported labels, and instructions for obtaining any separately distributed model files.

### Be honest about sign-language recognition

Do not claim that a small gesture classifier can translate unrestricted sign language.

Sign languages are complete languages with their own grammar and regional variation. Recognizing a few static gestures is not the same as translating continuous signing.

If reliable full sign-language translation is not feasible, implement a clearly defined and genuinely working limited-vocabulary prototype.

Document:

- Which signs are supported.
- Which sign language or dataset the model represents, if known.
- Whether recognition is static or continuous.
- Environmental constraints.
- Confidence limitations.
- Known failure cases.
- How new gestures could be added later.

Never make up random predictions to give the impression that recognition works. Display an uncertain or unrecognized state when appropriate.

The interface must distinguish a genuine model prediction from an example or demonstration mode.

Provide a manual fallback so a user can still enter text when the camera or recognition model is unavailable.

### Performance and privacy

Aim to keep processing on the laptop where practical.

Do not upload camera footage to a third-party service without a clear requirement, explicit user consent, and transparent disclosure.

Avoid recording or saving images or video unnecessarily.

## FEATURE B — MORSE DECODER

Implement a functional Morse-code encoder/decoder module.

### Required functionality

Support:

- Entering dots and dashes manually.
- On-screen dot and dash controls.
- A space or letter-separation control.
- Decoding Morse code into readable text.
- Clearing the input.
- Editing and correcting input.
- Inserting decoded text into the shared text workspace.
- Copying the decoded result.

Use the International Morse alphabet for letters and digits, along with sensible support for common punctuation.

Clearly define how letters and words are separated. Do not leave ambiguous input rules undocumented.

### Optional enhancement

If practical, implement a timing-based input mode that allows users to enter dots and dashes using a key or button.

If you implement timing-based detection, make the thresholds understandable and adjustable. Test it rather than assuming that timing will work consistently for everyone.

The manual mode must remain usable independently of the timing mode.

Write unit tests for the decoding logic, including valid sequences, spaces, digits, punctuation, unknown sequences, and empty input.

## FEATURE C — LIVE CAPTIONS

Create a speech-to-text interface using a suitable browser speech-recognition API or a well-justified alternative.

### Required functionality

The user should be able to:

- Read a clear explanation of the microphone permission requirement.
- Start listening.
- Stop listening.
- See the transcript appear as speech is recognized.
- Distinguish confirmed transcript text from interim recognition results where the chosen API supports that distinction.
- Read and edit the result.
- Clear the transcript.
- Add it to the shared text workspace.

Display understandable error messages when:

- Microphone access is denied.
- The browser does not support the chosen API.
- The microphone is unavailable.
- Recognition fails or stops unexpectedly.
- Network access is required by the browser's speech service.

Do not silently discard the text already captured when an error occurs.

### Compatibility

Browser speech-recognition support varies. Check the actual supported APIs and avoid promising identical behaviour in every browser.

If the selected browser cannot support live captions, clearly explain why and provide an appropriate fallback where practical.

If an offline or alternative speech-recognition implementation is considered, evaluate its model size, performance, dependencies, and laptop requirements before choosing it.

Never present mock transcript text as live speech recognition.

## FEATURE D — SHARED TEXT WORKSPACE AND READ ALOUD

This is the central feature of the application.

### Shared text workspace

Create a large, clearly labelled, editable text area.

The user should be able to:

- Type text manually.
- Insert recognized signs.
- Insert decoded Morse text.
- Insert captions.
- Edit text from any source.
- Copy all text.
- Clear the workspace after confirmation when appropriate.
- Download the text as a `.txt` file.
- Use the text with the Read Aloud feature.

Adding new text from a feature should follow a consistent rule. Do not unexpectedly overwrite existing text.

Where necessary, provide separate actions for replacing selected text and appending new text.

### Read Aloud

Use the browser's speech-synthesis functionality if suitable.

Provide:

- A Read Aloud button.
- A Stop button.
- A Pause/Resume control if supported.
- Voice selection where available.
- A reasonable speech-rate setting.
- An informative message when speech synthesis is unavailable.

Read the actual text in the workspace rather than hardcoded example text.

Handle empty text and interruptions gracefully.

Make sure the controls work with keyboard input and assistive technologies.
